## Context

入力は `geojson/` 配下の2ファイル（EPSG:6668／JGD2011緯度経度）:
- `N06-25_HighwaySection.geojson`: 路線データ（MultiLineString）1,500地物。属性
  `N06_001`〜`N06_011`。うち `N06_003`（設置期間終了年）が `9999` の1,289地物が
  現況。`N06_007`＝路線名、`N06_008`＝路線種別区分コード（1:高速自動車国道 / 2:
  高速自動車国道に並行する自専道 / 3:一般国道の自専道 / 4:本州四国連絡高速道路 /
  5:指定都市高速道路 / 6:その他）。
- `N06-25_Joint.geojson`: 地点データ（Point）2,479地物。属性 `N06_012`〜
  `N06_019`。うち `N06_014`（設置期間終了年）が `9999` の2,384地物が現況。
  `N06_018`＝地点名、`N06_019`＝接合部種別コード（1:一般IC[現況1,942] / 2:
  スマートIC[164] / 3:JCT[245] / 4:その他の接合部＝SA/PA接続等[33]）。

属性の意味は国土数値情報 製品仕様書（N06）およびコードリスト
（HighwayCatCd／HighwayUseCd／HighwayConCd）に基づく。時系列データではあるが、
本変更では過去の変遷は扱わず「現況（終了年=9999）」のみを対象とする（確定事項）。

配信はサーバー運用なしのPMTiles＋静的ホスティング、背景地図なしで高速道路
レイヤーのみを表示する（いずれもユーザーとの合意事項）。詳細な要求仕様は
`specs/highway-tile-pipeline/spec.md` と `specs/highway-map-viewer/spec.md` を
参照。本ドキュメントは実現方式（How）のみを扱う。

## Goals / Non-Goals

**Goals:**
- GeoJSON→（前処理）→tippecanoe→PMTilesの再現可能なビルドパイプラインを用意する。
- 地点データについて、重要度（種別）と密度の両面から、ズームレベルごとに収録数を
  制御するロジックを具体化する。
- MapLibre GL JSのスタイル定義（style.json相当）を、国土地理院の標準地図・
  Googleマップを参考にしつつ、このデータセットの属性（路線種別区分・接合部種別）
  に対応させる。
- ビルド成果物（PMTiles＋静的サイト一式）をそのまま任意の静的ホスティングに配置
  すれば動作する構成にする。

**Non-Goals:**
- 年代別の時系列表示・スライダーUI（確定事項によりスコープ外）。
- 背景地図（GSI・OSM等のベースマップタイル）の統合（確定事項によりスコープ外）。
- 検索・ルート案内・交通量表示などの付加機能。
- タイル生成の自動再実行（CI連携）や、原データ更新時の差分更新の仕組み。初回
  ビルド用の手動実行可能なパイプラインで十分とする。

## Decisions

### 1. タイル生成ツール: tippecanoe
GeoJSON→MVT変換のデファクトスタンダードであり、ズーム範囲指定
（`-Z`/`-z`）、属性の取捨選択、そして後述の密度ベース間引き
（`--drop-densest-as-needed` 等）や地物単位のズーム制御
（`tippecanoe` プロパティによる `minzoom` 指定）を単一ツールでまかなえる。
代替として独自のラスタライズ/簡略化スクリプトも検討したが、実績のある
オープンソースツールを使う方が信頼性・保守性で優る。

### 2. 出力フォーマット: PMTiles（mbtilesではなく）
確定事項（サーバーレス・静的ホスティング）に基づく。tippecanoeでmbtilesを
出力し、`pmtiles convert` でPMTilesへ変換する（tippecanoe自体がPMTiles出力に
対応していない版がある前提。対応版であれば直接出力してよい）。クライアントは
`pmtiles` protocolプラグインをMapLibre GL JSに登録し、HTTP Range Requestで
必要なタイルのみ取得する。

### 3. 現況フィルタリングは前処理ステップで実施
tippecanoeに渡す前に、GeoJSONを読み込み `N06_003`（路線）／`N06_014`（地点）が
`9999` の地物だけを抽出するスクリプト（前処理）を用意する。tippecanoe自体には
属性値によるフィルタ機能が限定的なため、事前にGeoJSONレベルで絞り込む方が
シンプルで検証しやすい。

### 4. 路線レイヤーの属性とズーム
前処理で `N06_007`（路線名）・`N06_008`（路線種別区分）のみを残した現況地物を
`tippecanoe -Z4 -z14` でタイル化する。ズームごとの間引きは行わず、tippecanoeの
標準的なライン簡略化（zoomレベルに応じたジオメトリ簡略化）に任せる。理由:
路線は密度過多にはならず（現況1,289地物）、低ズームでの見やすさはジオメトリ
簡略化とスタイル側の線幅・ラベル制御で十分に確保できる。

### 5. 地点レイヤーの重要度ランク付けとズーム制御
前処理で各地点に `N06_019` に基づく重要度ティアを付与し、tippecanoeの地物単位
`minzoom` に変換する:

| 種別（N06_019） | 重要度ティア | minzoom |
|---|---|---|
| 3: JCT | 0（最重要） | 8 |
| 1: 一般IC | 1 | 10 |
| 2: スマートIC | 2 | 12 |
| 4: その他の接合部 | 3 | 14 |

この`minzoom`を地物ごとのtippecanoe `tippecanoe.minzoom` プロパティとして埋め
込み、`tippecanoe -Z8 -z14 --minimum-zoom=8` でタイル化する。これにより、
「あるズームで収録される種別集合は、より低いズームの集合を包含する」という
spec要件（順序保証）を、tippecanoeの標準機能だけで満たす。

閾値（8/10/12/14）は、現況地物数（JCT 245／一般IC 1,942／スマートIC
164／その他 33）と国内の空間分布から、低ズームでの過密を避けつつ主要な結節点
から段階的に情報量を増やす目安として設定した設計値であり、実装時のビジュアル
確認で微調整してよい（spec上は「順序を守った段階的な追加」が要件であり、具体的
なズーム数値は規定していない）。

### 6. 密度ベースの間引き
上記のminzoom割り当てだけでは、大都市圏（首都高・阪神高速周辺等）でJCT/ICが
局所的に密集し、z8〜z13で依然としてタイルが過密になり得る。これに対し
tippecanoeの `--drop-densest-as-needed`（または同等の密度ベース間引きオプション）
を各ズームに適用し、tile-join時点でのタイルサイズ／地物密度の上限を超える場合に
限り、そのタイル内で重要度の最も低い地物から間引く。z14相当のレイヤーは間引き
対象から除外し（`--full-detail`や最大ズーム専用のtippecanoe設定を用いる、または
z14を別レイヤー/別ビルドとして密度間引きなしで生成する）、現況地点の完全収録を
保証する。この保証は実装時に「z14タイル群からデコードした地物数の合計＝現況
地点数（2,384）」を検証するスクリプトで確認する。

### 7. 路線スタイル: 国土地理院 最適化ベクトルタイル（標準地図）を参考に
GSIの標準地図における道路表現（ケーシング＋フィルの二重描画、道路種別・
ズームに応じた線幅/配色のグラデーション、高速道路系統をオレンジ〜赤系の配色で
強調する方針）を参考に、MapLibreスタイルでも `line` レイヤーをケーシング用と
フィル用の2レイヤーに分け、`line-width` と `line-color` を `["interpolate", ...]`
でズーム連動させる。`N06_008`（路線種別区分）の値によって配色・線幅の
バリエーションを持たせる（例: 高速自動車国道系統は最も太く濃い配色、指定都市
高速道路やその他は控えめな配色）。正確な配色・線幅の数値は、実装時にGSI
最適化ベクトルタイルの公開スタイル定義を確認しながら調整する（実装詳細のため
tasks.mdで扱う）。

### 8. 路線名ラベル: `symbol-placement: "line"`
MapLibreの`symbol`レイヤーで `symbol-placement: "line"`、
`text-field: ["get", "route_name"]` を用い、ラインに沿って路線名を繰り返し
配置する。`text-allow-overlap: false` とMapLibre標準の衝突検出により、近接
ラベルの重なりを回避する。

### 9. 地点スタイル: Googleマップを参考にしたマーカー表現
Googleマップの地点表現（丸みを帯びたピン/アイコン、種別ごとの配色・アイコン
差別化、ズームに応じたサイズ変化）を参考に、`circle`または`symbol`レイヤーで
`N06_019`（接合部種別）に応じたcase式の配色・サイズ分岐を行う（例: JCTは
目立つ配色・やや大きめ、一般ICは標準、スマートICはIC系だが区別できる配色、
その他は控えめ）。ラベル（地点名）は`symbol`レイヤーで`text-field`を設定し、
minzoomはタイル側で既に種別ごとに制御されているため、レイヤー側は
特別なズーム式なしでそのまま表示すればspec要件（重要度順の段階的表示）を満たす。

### 10. 静的サイト構成
ビルド成果物として、`index.html` ＋ MapLibreスタイル定義（JSまたはJSON）＋
生成された2つのPMTilesファイルを1つの出力ディレクトリにまとめる。MapLibre GL
JSおよびPMTiles protocolプラグインはCDN配信のビルド済みバンドルを利用し、
Node.js等のビルドステップをクライアント側に必須としない（開発時のローカル確認
用に軽量な静的サーバーは使う）。

## Risks / Trade-offs

- [tippecanoeの `tippecanoe` プロパティによるminzoom制御と`--drop-densest-as-needed`
  の組み合わせ結果が意図通りにならない可能性] → 実装時に主要ズーム
  （8/10/12/14）でタイルをデコードし、収録種別・件数を検証するチェックスクリプト
  をtasksに含める。
- [GSI最適化ベクトルタイルの正確な配色・線幅を厳密に再現するわけではない
  （「参考にする」レベル）] → specでも「参考にしたスタイル」を要件としており、
  ピクセル単位の一致は求めない。実装時に見た目のレビューで妥当性を確認する。
- [地点minzoom閾値（8/10/12/14）が実際の分布に対して粗すぎる/細かすぎる可能性]
  → 設計値であり固定要件ではないため、実装後のビジュアル確認で調整可能
  （spec上の「順序保証」さえ壊さなければ変更は本設計のマイナー修正で済む）。
- [CDN配信のMapLibre GL JS/PMTilesプラグインへの外部依存] → 静的ホスティングの
  簡潔さを優先するトレードオフとして許容する。オフライン/社内配信が必要になれば
  ライブラリをローカルにバンドルする変更を別途行う。

## Migration Plan

グリーンフィールドの新規構築のため、既存システムからの移行は発生しない。
デプロイは「タイル生成パイプラインを実行 → 出力ディレクトリ（PMTiles＋静的
サイト一式）を任意の静的ホスティング先にアップロード」の一方向のみ。ロール
バックは、静的ホスティング先の直前のデプロイ済みファイル一式に戻すだけで良い。
