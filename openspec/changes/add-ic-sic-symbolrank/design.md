## Context

`add-jct-symbolrank`変更により、`pipeline/preprocess/filter_points.py`はJCT（`point_type`が`3`）に限り、接続する路線の車線数合計から`symbolrank`（`1`〜`3`）を算出し、`JCT_SYMBOLRANK_MINZOOM`（`{1: 8, 2: 9, 3: 10}`）でタイル収録`minzoom`を決定している。一般IC（`point_type`が`1`）・スマートIC（`point_type`が`2`）は現在も`POINT_TYPE_MINZOOM`の固定値（IC=10、SIC=12）のままである（[[main spec]] `highway-tile-pipeline`の「地点データの重要度に基づくズーム選別」要件）。`site/style/map-style.js`の`point-labels`レイヤーは、`symbol-sort-key`をJCTは`symbolrank`、IC/SIC/その他は種別ごとの固定値（IC=4、SIC=5、その他=6）で決定している。

本変更が新たに参照する人口データ（`geojson/250m_mesh_2024_GEOJSON/`、94ファイル・合計約7.7GB、Git管理対象外）は、国土数値情報「250mメッシュ別将来推計人口」で、1地物＝1つの250m四方メッシュ（`Polygon`ジオメトリ）を表し、`PTN_2025`属性に2025年の総数人口（男女計、小数、未算定は`null`）を持つ。座標系はJGD2011（EPSG:6668、緯度経度）。ファイルは1次メッシュ相当の地域ごとに94分割されているが、各ファイルが具体的にどの範囲をカバーするかを示す索引は付属しない。

対象となるIC・SICは合計2,106件（IC 1,942件・SIC 164件）。既存の`spatial_match.matching_values`による頂点一致判定で、IC/SICの約90%（1,893件）は接続する路線地物の法定路線名（`route_name`）が単一に定まり、約10%（212件）は2〜3件の異なる`route_name`に接続する（路線境界に位置する地点）。

## Goals / Non-Goals

**Goals:**
- IC・SIC（`point_type`が`1`または`2`）に、周辺人口に基づく`symbolrank`（`2`〜`5`）を新設する。
- IC・SICのタイル収録`minzoom`を、`symbolrank`に応じた段階（9／10／11／12）に変更する。
- IC・SICの地点名ラベルの衝突優先順位を、種別（IC/SIC）ではなく`symbolrank`（人口）で決定する形に変更しつつ、JCTが常に最優先という既存の階層は維持する。

**Non-Goals:**
- JCT・その他の接合部への本変更の適用（対象外のまま）。
- `lane_counts`・JCTの`symbolrank`（車線数合計ベース）の算出ロジックの変更。
- 人口メッシュデータの增分更新・キャッシュの永続化。パイプライン実行のたびに`geojson/250m_mesh_2024_GEOJSON/`から再計算する（既存の`filter_lines.py`・`filter_points.py`と同じ「毎回`geojson/`から再構築する」方針を踏襲）。
- 人口データの将来年（2030年以降）の利用。2025年総数人口（`PTN_2025`）のみを用いる。
- 10km圏内人口の算出精度の測地線（geodesic）厳密計算。後述の決定2の近似で十分とする。

## Decisions

### 決定1: 周辺人口メッシュの探索は、94ファイルを1回ずつ順次読み込むフルスキャン方式とする
94ファイル（合計約7.7GB）を、点群ごとに個別に絞り込んで読み込むのではなく、ファイル単位で1回だけ読み込み、その場で全2,106地点との距離判定・人口加算をNumPyのベクトル演算で行う。ファイルごとにメッシュ中心点の緯度経度配列と`PTN_2025`配列を構築し、2,106地点の座標配列とのブロードキャスト演算で一括して10km以内判定・合算を行う。1ファイルあたりのメッシュ数は最大でも数十万件程度であり、2,106地点との距離演算はNumPyで数秒以内に収まる規模のため、事前のファイル選別（1次メッシュ座標からの索引構築等）を行わなくても全体のI/Oコスト（7.7GBの1回読み込み、ボトルネックはディスクI/O）に対して計算コストは無視できる。

代替案として検討したが不採用:
- **各ファイルの空間範囲（バウンディングボックス）を事前に索引化し、地点ごとに関係するファイルのみ読み込む**: I/O量を削減できる可能性があるが、索引構築自体に全ファイルの走査が必要（または未検証のメッシュコード命名規則への依存が必要）で、実装が複雑になる割にI/O量の削減効果が小さい（結局7.7GB全体を一度は読む必要がある）ため不採用。

### 決定2: メッシュ中心点との距離は緯度補正した平面近似（正距円筒図法近似）で算出する
メッシュポリゴンの中心点は、ジオメトリの外環座標の最小・最大値の中点（バウンディングボックス中心）から求める（Shapelyの`centroid`計算を全メッシュに適用するより高速）。地点座標との距離は、地点の緯度で経度方向のスケールを補正する平面近似式（`dx_km = Δlon * 111.32 * cos(lat_rad)`、`dy_km = Δlat * 110.57`、`distance = sqrt(dx_km^2 + dy_km^2)`）で算出し、10km以下のメッシュの`PTN_2025`（`null`は0として扱う）を合算する。

代替案として検討したが不採用:
- **Haversine式や測地線ライブラリによる厳密な距離計算**: 10km程度のスケールでは平面近似との誤差が無視できるレベル（高々数十m）であり、追加の依存や計算コストに見合わないため不採用。

### 決定3: `symbolrank`は接続路線（`route_name`の組）内での人口順位を四分位で4分割して決定する
IC/SIC地点を、接続する路線地物の法定路線名（`route_name`）の集合（frozenset）をキーにグループ化する（決定4参照）。各グループ内で人口降順に順位付けし（同順位は`point_name`昇順でタイブレーク）、`n`件のグループ内で`r`番目（`1`始まり、人口が多い方から）の地点には、`symbolrank = 2 + floor((r - 1) * 4 / n)`を割り当てる。この式は、グループサイズ`n`が4の倍数でない場合や`n < 4`の場合でも、人口順位に応じてなるべく均等な段階に分割される（例：`n=1`は常に`symbolrank=2`、`n=2`は`2`・`4`、`n=4`は`2`・`3`・`4`・`5`）。

代替案として検討したが不採用:
- **固定の人口閾値（全国一律）で`symbolrank`を決定する**: 都市部と地方部で人口分布の桁が大きく異なり、地方の路線ではほぼ全地点が下位ランクに偏り、都市部の路線ではほぼ全地点が上位ランクに偏るため、「路線ごとに表示密度を均一にする」というユーザー確認済みの要件を満たせず不採用。
- **単純な等分割（`n // 4`件ずつ）で切り捨て、余りを最上位グループに寄せる**: 端数の扱いが恣意的になり、`n`が小さい場合に不自然な偏りが生じるため、順位ベースの式（上記）を採用。

### 決定4: 複数の`route_name`に接続する地点は、接続する`route_name`の組を1つの複合グループとして評価する
IC/SICの約10%（212件）は接続する路線地物の`route_name`が複数（2〜3件）ある。これらの地点は、単一の`route_name`ごとに別々のグループへ分類するのではなく、接続する`route_name`の組（frozenset、順不同）をキーとする1つの複合グループとして扱う（ユーザー確認済み）。接続する路線地物が1件もない地点（実データで1件）は、自身の`point_name`のみをキーとする単独グループ（`n=1`）として扱い、常に`symbolrank=2`となる。

代替案として検討したが不採用:
- **接続する各`route_name`のグループで個別に評価し、最良のsymbolrankを採用する**: 複数路線の人口相対順位を横断的に比較することになり、「路線ごとの相対評価」という設計意図から外れるため不採用（ユーザー確認済み）。

### 決定5: IC・SICの`minzoom`は`symbolrank`から導出する固定マッピングを用いる
`POINT_TYPE_MINZOOM`のIC・SIC向け固定値（10・12）を廃止し、`IC_SIC_SYMBOLRANK_MINZOOM = {2: 9, 3: 10, 4: 11, 5: 12}`を新設して、地物ごとの`tippecanoe.minzoom`を`symbolrank`から決定する（ユーザー指定値）。JCT・その他の接合部の`minzoom`決定ロジックは変更しない。

### 決定6: `symbol-sort-key`は、IC/SICの`symbolrank`にオフセットを加算し、JCT・その他の既存の優先順位帯と重複しないようにする
現行の`symbol-sort-key`は、JCTが`symbolrank`（`1`〜`3`）、IC=固定`4`、SIC=固定`5`、その他=固定`6`という値の帯を使用している。IC/SICの`symbolrank`（`2`〜`5`）をそのまま`sort-key`に使うとJCTの帯（`1`〜`3`）と重複し（例：`symbolrank=2`のICが`symbolrank=3`のJCTより優先されてしまう）、「JCTが常に最優先」という既存要件を壊す。これを避けるため、IC/SICは`symbolrank + 3`（値域`5`〜`8`）を`sort-key`として使用し、その他の固定値を`6`から`9`に引き上げる（JCT: `1`〜`3` ＜ IC/SIC: `5`〜`8` ＜ その他: `9`という帯に再配置する）。IC・SICの間で種別による優先順位は設けず、同じ`symbolrank`帯を共有する（`symbolrank`が小さい方が種別を問わず優先）。

代替案として検討したが不採用:
- **IC・SICそれぞれに別々のオフセットを設け、同一symbolrankでもIC優先を維持する**: 周辺人口によるランキングという本変更の趣旨（種別を問わず人口の多い地点を優先表示する）に反するため不採用（ユーザー確認済みの通り、IC・SIC間の種別階層は本変更で解消する）。

## Risks / Trade-offs

- [Risk] 7.7GBのメッシュデータをビルドのたびにフルスキャンするため、`pipeline/preprocess/run.sh`の実行時間が大きく増加する（数分〜十数分程度を想定） → 一度きりのバッチ処理であり、実行頻度（変更のたびに手動実行）を考えれば許容範囲とする。将来的にI/O時間が問題になる場合は、決定1のファイル選別索引化を別変更で検討する。
- [Risk] 1ファイル最大約509MBのJSONを`json.load`で読み込むため、実行時に数GB規模のメモリを要する → ビルド実行環境に十分なメモリ（目安4GB以上の空き）があることを前提とする。将来的にメモリ制約が問題になる場合は、ストリーミングパーサ（`ijson`等）への切り替えを別変更で検討する。
- [Risk] 決定3の順位ベースの四分位式は、グループサイズが小さい路線（`n<4`）では`symbolrank=5`が付与されにくい偏りが生じる → 路線ごとの表示密度を均一にするというユーザー要件に対する意図的なトレードオフとして許容する（`verify_counts.py`でグループサイズ別の`symbolrank`分布を出力し、著しい偏りがあれば別途見直す）。
- [Trade-off] `symbol-sort-key`のその他の接合部の固定値を`6`から`9`に変更するため、その他の接合部同士のラベル衝突優先順位の相対関係自体は変わらないが、数値そのものが変わる（振る舞いへの影響はない）。

## Migration Plan

1. `pipeline/preprocess/point_population.py`を新設し、IC/SIC地点座標のリストを受け取り、`geojson/250m_mesh_2024_GEOJSON/`の94ファイルを1回ずつ読み込みながら各地点の半径10km以内人口合計をNumPy配列演算で算出する関数を実装する（決定1・決定2）。
2. `pipeline/preprocess/filter_points.py`に、IC/SICの接続路線`route_name`（複数の場合は組）によるグループ化、グループ内人口相対順位からの`symbolrank`算出（決定3・決定4）、`symbolrank`から`minzoom`を導出するロジック（決定5）を追加する。
3. `pipeline/preprocess/verify_counts.py`に、IC/SICの`symbolrank`属性・ランク別件数（グループサイズ分布を含む）の検証を追加する。
4. `pipeline/preprocess/run.sh`を実行し、`points.current.geojson`が期待通り生成されることを確認する（実行時間の実測を含む）。
5. `pipeline/tilegen/verify_tiles.py`に、IC/SICの`symbolrank`別ズーム収録（`z9`は`symbolrank=2`のみ、`z12`以降は全IC/SIC）の検証を追加する。
6. `./pipeline/build.sh`を実行し、`site/tiles/points.pmtiles`を再生成・配置する。
7. `site/style/map-style.js`の`point-labels`レイヤーの`symbol-sort-key`を、決定6のオフセット方式に変更する。
8. `pipeline/preprocess/README.md`に、新設スクリプトの依存関係（NumPy、人口メッシュデータ）を追記する。
9. `npx serve site`でローカル動作確認（IC/SICの`symbolrank`別表示開始ズーム、人口の多いSICが人口の少ないICより先に表示されること、JCTが常に最優先のままであること、その他の接合部の表示に変化がないことを含む）を行う。
10. `main`への`site/**`・`pipeline/**`変更pushで、`site/**`分は既存のGitHub Actionsが自動デプロイする。タイル（`site/tiles/points.pmtiles`）の再生成・配置はビルドスクリプト実行が必要なため、手動での配置確認も行う。
